Can the Coach deepen a thought without becoming its author?

This demo tests a versioned state and response contract for one-question-at-a-time Thought Development. It makes prerequisites visible, forbids Coach-supplied substance, defines a real completion test, and returns only a faithful summary while leaving the Article unchanged.

Proposed Coaching Contract

Persistent session state: Writer substance and decision topology

        
Turn request: one current frontier node plus the unchanged Article

        
Turn response: one question, state patch, or completion

        
Prompt guidance: ownership and questioning rules
1. Develop exactly the Writer's selected rough thought. Do not broaden into brainstorming.
2. Treat the Article and every Writer answer as the only sources of substantive claims, examples, evidence, experiences, reasons, and conclusions.
3. Ask exactly one neutral, useful question per turn. Do not include suggested answers, multiple-choice options, leading premises, praise, or replacement prose.
4. Choose the first ready node from the prerequisite-aware frontier. Never ask a question whose prerequisites are unresolved.
5. After each Writer answer, extract only supported atomic notes, record their source turn IDs, update the addressed node, and recompute the frontier.
6. If an answer is ambiguous, contradictory, or says "I don't know," stay on that node with one narrower question or let the Writer skip it. Never fill the gap.
7. A session is complete only when no required node is ready or blocked, every required node is answered or explicitly skipped, and the Article role is clear.
8. On completion, summarize the Writer's supplied thinking with source-note IDs. Label unresolved tensions and skipped gaps. Do not turn notes into publishable prose.
9. Never mutate the Article. Return its start revision and content hash; the client verifies both before restoring focus to the same selection.
10. The Writer may exit at any time. Early exit returns a partial summary, unresolved frontier, and the unchanged Article restoration data.

        
Deterministic application validation
Reject a turn response unless:
- contractVersion, sessionId, and turnId echo the request;
- response kind is exactly question, state_patch, or complete;
- question responses contain exactly one question and target one ready node;
- every extracted note cites a Writer turn and is textually entailed by it;
- node and dependency IDs already exist or are valid additions under the selected thought;
- no required unanswered node is omitted from both frontier and blockedNodes;
- complete=true passes the application's completion predicate;
- summary claims cite existing active note IDs;
- articleRevision and articleContentHash still match session start.

The client, not the model, applies the patch, recomputes the frontier, tests completion, and restores the unchanged Article selection.

Decision this prototype is testing
Use a client-owned decision tree with explicit node prerequisites and source-linked Writer notes. Let the model propose one frontier question or a narrow state patch, but let deterministic application logic own validation, frontier recomputation, completion, summary traceability, and proof that the Article was not changed.
